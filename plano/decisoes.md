# Registro de decisões

| Data | Decisão | Motivo / evidência |
|---|---|---|
| 2026-10-17 | Estrutura de validação criada (plano vivo + 6 agentes) | Início do projeto |
| 2026-10-17 | Ideia registrada (v0.1). Hipótese de começar B2B (ferramenta para a operação do sócio) antes do marketplace B2C | Evita o problema do ovo e da galinha; aproveita a rede do sócio e a experiência do fundador com inventário compartilhado. A validar com H1-H4 |
| 2026-10-17 | Pesquisa de mercado concluída. A hipótese B2B se fortalece: foco na **rede** (inventário multi-operadora compartilhado + split de Pix), não em mais um sistema para receptivo. B2C fica para depois | B2C dominado pela Civitatis (US$ 50 mi captados, presente em 26 estados + DF). Já existem sistemas B2B BR, mas sem foco em rede. Ver `02-mercado.md` |
| 2026-10-17 | Praça inicial: **cidade do Rio de Janeiro**. Expansão só depois de densidade local | O sócio opera fisicamente no Rio; um marketplace/rede depende de densidade local, não de cobertura nacional |
| 2026-10-17 | **Correção do fundador:** o produto é um portal B2C que conecta turistas a passeios (modelo iFriend / Airbnb Experiências), não uma ferramenta de gestão. A hipótese B2B foi descartada | Visão do fundador. Os riscos do B2C (aquisição, diferencial) passam a ser os principais a validar (H9-H11) |
| 2026-10-17 | Modelo: marketplace de dois lados (B2B2C), começando pela oferta: primeiro as operadoras do sócio cadastram os passeios, depois vêm as ferramentas para o turista achar e comprar | A oferta inicial já está garantida pela rede do sócio. Começar pela oferta é a estratégia clássica de marketplace |
| 2026-10-17 | Criado `pitch.md` como documento vivo, preenchido conforme as hipóteses são validadas | Facilitar a venda da ideia a sócios, operadoras e investidores |
| 2026-10-17 | Desenhado o experimento 01 (QR code com promotores) em `experimentos/exp01-qrcode.md` | Testar H9/H10 com custo mínimo antes de construir o MVP |
| 2026-10-17 | Incorporada a operação real do sócio (Grupo Rio/Inside) a partir da documentação do Rio Manager (`../grupo_rio/manager/`). Ver `pesquisa/grupo-rio-operacao.md` | Números reais substituem hipóteses: ≈ R$ 526 mil vendidos, ≈ 23% de intermediação |
| 2026-10-17 | Números da Inside (R$ 526 mil, 701 reservas, ≈23% de intermediação) marcados como **não confirmados** | O fundador suspeita que sejam dados de teste. `dashboards.md` diz que vieram da planilha do cliente. Confirmar com o sócio |
| 2026-10-17 | Números da Inside **descartados**: eram mock do seed do Rio Manager | Confirmado pelo fundador. Ficam só as regras de negócio. Números reais: pedir ao sócio |
| 2026-10-17 | Incorporados os dados reais da Inside (fev-out/2026): ≈ R$ 90 mil/mês, intermediação 22%, 95% hispanofalantes, 75% compram até a véspera. Ver `pesquisa/inside-dados-reais-2026.md` | Planilhas do sócio. Dados pessoais não copiados para o repositório |
| 2026-10-17 | Portal trilíngue desde o início: português, espanhol e inglês | Fundador quer atender todo o público, não só a base atual (95% hispanofalante) |
| 2026-10-17 | **Experimento 01 (QR code) pulado.** Seguir direto para o MVP | Fundador: a demanda já existe (vendas na praia) e ele assume o risco do tempo de desenvolvimento. Risco aberto: H14 (turista comprar sozinho, online), que passa a ser medida no MVP |
| 2026-10-17 | Modelo definido: **marketplace gerenciado com roteamento**. O turista compra o produto, e a plataforma aloca a operadora por disponibilidade e margem (como a Inside faz hoje). A operadora não aparece para o turista como vendedora | A Inside é intermediária: não detém passeios e escolhe entre várias operadoras por produto |
| 2026-10-17 | **Modelo redefinido pelo fundador: marketplace aberto.** O turista escolhe passeio e operadora (filtros e mapa), as operadoras cadastram os próprios passeios, o pagamento total é feito na plataforma e o repasse vem depois. Interfaces: turista, operadora e admin. A Inside não tem papel; só a rede de operadoras é migrada. Roteamento descartado | Visão do fundador |
| 2026-10-17 | Sistema novo e independente. A documentação e os dados da Inside/Rio Manager são só referência de domínio | Correção do fundador: o MVP v1 assumia reaproveitar o backend do Rio Manager |
| 2026-10-17 | Login obrigatório para reservar (Google ou código por e-mail, sem senha). Catálogo aberto sem login | Fundador prefere conta para pagamentos; login com Google é rápido e seguro |
| 2026-10-17 | Stack: Python (FastAPI) + PostgreSQL + Redis (fila/cache). Reservas no Postgres | Preferência do fundador |
| 2026-10-17 | MVP v2 registrado em `05-mvp.md`. Pendentes: site primeiro vs. app desde o início; prazo de confirmação (recomendado 2h); comissão | Aprovado pelo fundador ("temos um MVP") |
| 2026-10-18 | **Reserva instantânea como padrão**: vaga na agenda → voucher na hora. Confirmação manual só para passeios sob consulta (15-30 min), fora da busca do mesmo dia. Vendas fecham X horas antes da saída | 2h de confirmação é incompatível com turistas decidindo na hora |
| 2026-10-18 | Proteção contra desintermediação no MVP: esconder contato e localização exata da operadora antes da reserva, moderação de contatos, vagas sem número exato, paridade de preço e regras nos termos | Risco levantado pelo fundador; nova hipótese H10 |
| 2026-10-18 | Comissão da plataforma: **10% padrão**, editável individualmente por operadora no painel admin | Decisão do fundador |
| 2026-10-18 | Promotores de praia fora do escopo por enquanto | Decisão do fundador |
| 2026-10-18 | Plataforma do MVP: **site responsivo e instalável (PWA)**. Apps iOS/Android com Expo na fase 2, usando a mesma API | Mais rápido, usa a experiência web do fundador, aparece no Google e o turista não precisa baixar nada |
| 2026-10-18 | Revisão crítica do MVP registrada em `gargalos.md`. Construir o MVP primeiro e eliminar os gargalos um a um depois | Decisão do fundador: ter noção do produto antes de atacar demanda, economia, tributação e prazo |
| 2026-10-18 | Criados `spec.md` (v0.1) e `tasks.md` na raiz. Proposta técnica: um único app Next.js para site, painel e admin; worker `arq`; PostGIS para proximidade | Evitar decisões técnicas implícitas no código; reduzir as bases de frontend (G9) |
| 2026-10-18 | Frontend: **SPA com Vite + React + TypeScript**, reaproveitando a configuração de fundação do Rio Manager (Vite, TS, Tailwind, shadcn, React Router, TanStack Query, RHF + Zod, i18next). Backend FastAPI com a mesma estrutura de pastas. Só configuração e padrões: nenhum código de domínio do Rio Manager | Decisão do fundador: reaproveitar o tempo investido na fundação |
| 2026-10-18 | Integrações (Google, SMTP, gateway, armazenamento, Sentry, mapa) só por variáveis de ambiente no backend, com `docs/integracoes.md`. App nasce com autenticação, roles, middlewares, rate limit e segurança. Bancos em Docker (Postgres + PostGIS, Redis, Mailpit). Princípios de escalabilidade baratos desde já | Decisão do fundador |
| 2026-10-18 | Frontend: **React Router v7 em modo framework** (Vite). SSR nas páginas públicas (SEO e 4G); `/painel` e `/admin` só no navegador; navegação fluida depois da primeira carga | O fundador quer navegação fluida, mas as páginas públicas precisam de SEO para aquisição de turistas (G1) |
| 2026-10-18 | Mapa 100% gratuito por enquanto: MapLibre GL JS + OpenFreeMap; geocodificação via Photon/Nominatim pelo backend | Decisão do fundador |
| 2026-10-18 | Infraestrutura de login completa, mas **desligada** (`AUTH_ENABLED=false`) com usuário de desenvolvimento por papel e seletor no frontend. Bloqueado em produção | O fundador quer testar as funcionalidades sem login por enquanto |
